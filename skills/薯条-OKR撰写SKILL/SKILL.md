# OKR 撰写

## 这个 skill 做什么、不做什么

- **做**：读上级和同组的 OKR，起草一份能对齐、可验收、格式和公司一致的个人 OKR，并说明每一条的来源。
- **不做**：不替员工决定做什么项目；不打分（score 是季度末评分，不是进度）；**没有本人明确同意，不往飞书写任何东西**。
- 起草时不能确定的日期、数字、范围，一律标【待确认】，不自己编。

## 固定流程（每次都走，不跳步）

### 第 0 步：确认对象和周期

问清楚三件事（能从上下文看出来的就不问）：给谁写、哪个周期（默认当前季度，不是年度周期）、有没有现成的 OKR 链接或上级是谁。

### 第 1 步：读链路

命令细节见 `references/lark-cli读写OKR.md`。

1. `contact +search-user` 拿到本人的 open_id 和部门；`okr +cycle-list` 拿到本人当季周期 id，看是否已经写过。
2. 找一个起点 okr_id：员工给的链接里的 `okrId`、上级的周期 id，或者本人自己的周期 id（如果已有对齐）。
3. 运行 `scripts/okr_crawl.py --seed <okr_id> --out <临时目录>`，沿对齐关系爬出整张网，得到 `tree.md`（自上而下的树）和 `dump.md`（每人的 O / KR）。
4. 在 `dump.md` 里 grep 本人姓名，找出所有 **@到本人的 KR**。@本人的上级就是要承接的人。顺着 `tree.md` 往上读到 CEO，列出这条链。

### 第 2 步：盘点三类输入

| 输入 | 从哪来 | 用途 |
|---|---|---|
| 必须承接的 KR | 上级 KR 里 @本人的条目 | 每一条都要在本人 OKR 里有对应 |
| 组内模板 | 同一上级下 2–3 位同事的 OKR | O 的命名方式、统一的软技能 O、权重习惯 |
| 本人实际在做的事 | 周报、项目文档、员工自述 | 补上级没写但确实在做、且对上级目标有贡献的事 |

先用表格把这三类输入列给员工看，**问一次**：有没有漏掉的项目、有没有不想放进来的。

### 第 3 步：起草

按 `references/公司OKR写法规范.md` 写。要点：

- 3–5 个 O，每个 O 2–4 条 KR；O 的权重加起来是 100，每个 O 下 KR 的权重加起来也是 100。
- 每个 O 写明对齐到谁的哪个 O。一个 O 对齐不上任何上级目标的，要么删，要么放低权重并说明理由。
- KR 写成：**时间点 + 交付物 + 验收标准（+ @协同人）**。
- 组内有统一模板 O（例如软技能）的，原文照搬，不改字。

### 第 4 步：自检（逐条过，不通过就改）

- [ ] 上级 @本人的每条 KR 都有承接，且承接的 O 挂了对齐
- [ ] O 权重合计 100，每个 O 下 KR 权重合计 100
- [ ] 每条 KR 都能在季度末回答"做到了没有"（有日期、有交付物、有标准）
- [ ] 没有把"做事"写成 O（例如"参加评审"），O 写的是要达成的结果
- [ ] 没有编造的数字和日期，不确定的都标了【待确认】
- [ ] 组内模板 O 和同事原文一致

### 第 5 步：交付

输出两份内容：

1. **表格版**（给员工看结构）：O（权重）｜KR（权重）｜对齐到｜来源（上级 @ / 组内模板 / 本人工作）。
2. **粘贴版**（可直接填进飞书）：按 `O1 …` / `KR1 …` 逐行排列，权重写在括号里。

然后问员工：要不要写进飞书？只有员工明确说写，才按 `references/lark-cli读写OKR.md` 的"写入"一节操作：写入前用 `--dry-run` 给员工看最终 JSON，创建 O / KR → 设权重 → 挂对齐，完成后用 `+cycle-detail` 读回来核对一遍。
